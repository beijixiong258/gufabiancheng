# 后端公共机制

> 技术版本见 [开发总览](./1.开发总览.md)。

本文件集中说明接口之外的通用后端设计：Redis Token、认证授权拦截器、MVC配置、校验、异常、时间字段和敏感字段保护。

## 1. Redis Token与请求头

第一版使用Redis保存简单Token，不使用Spring Security、JWT和OAuth。

登录请求：

```http
POST /yonghu/login
Content-Type: application/json
Accept: application/json

{"zhanghao":"zhangsan","mima":"123456"}
```

登录成功后：

1. 使用项目 `Utils.generateId()` 生成Token。
2. Token为去除UUID连字符后的32位字符串。
3. 在Redis中保存Token对应的用户ID，并设置4天有效期。
4. 将Token字符串放入登录接口的统一响应数据中。

登录管理类内部使用 `StringRedisTemplate`，保存结构：

```text
login:{token} → yonghuId
```

Redis通过Docker数据卷和AOF保存数据。Token是否有效仍以Redis中的Key及其TTL为准。

## 2. Token使用约定

后续需要登录的请求携带：

```http
Authorization: Bearer 550e8400e29b41d4a716446655440000
```

约定：

- Token由登录接口生成，客户端不能自行指定。
- 不接受前端提交的用户ID或 `quanxian` 作为当前身份。
- 拦截器只相信Token对应的服务端用户ID，并从数据库查询最新用户和权限。
- 退出登录时从Redis中删除当前Token。
- Token固定有效期为4天，普通业务请求只验证Token，不自动续期。
- 前端每次启动应用且本地存在Token时调用 `POST /yonghu/refresh`。
- Token剩余时间大于5小时时刷新接口返回原Token；剩余时间小于等于5小时时删除旧Token并创建新Token。
- 前端统一保存刷新接口返回的Token；Token已经过期时重新登录。
- JSON请求使用 `Content-Type: application/json`。
- 客户端建议发送 `Accept: application/json`。

## 3. 拦截器与MVC配置

当前使用一个 `AuthInterceptor` 同时完成登录认证和管理员授权。它读取：

```http
Authorization: Bearer <token>
```

拦截器默认保护 `/**`，放行：

```text
POST /yonghu/register
POST /yonghu/login
/error
```

路径等于 `/admin` 或以 `/admin/` 开头的接口额外检查 `ADMIN` 权限。管理员方法统一放在类级映射为 `/admin` 的 `GuanliyuanController` 中。

`AuthInterceptor` 使用 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE` 取得Spring MVC实际匹配到的接口路径，再进行管理员路径判断，不直接比较客户端发送的原始URI。

处理顺序：

```text
AuthInterceptor认证并按路径授权 → Controller → Service归属检查
```

在实现 `WebMvcConfigurer` 的配置类中注册拦截器。拦截器将 `yonghuId`、`token` 和 `quanxian` 放入request属性；Controller使用 `@RequestAttribute` 取得。记录、会话、消息是否属于当前用户仍由Service查询确认。

拦截失败时抛出 `CommonException`，由全局异常处理器返回统一 `Result`。

## 4. 请求参数校验

写入接口使用独立请求对象，按需要添加：

```java
@NotBlank
@Size
@Email
@Pattern
```

Controller中的JSON参数使用：

```java
@Valid @RequestBody ...
```

管理员修改用户使用 `GuanliyuanXiugaiDTO` 并在Controller中执行Bean Validation。ID、账号和权限必填；密码为可选字段，空白时保留原密码，非空时必须为6至32位并在Service中执行BCrypt哈希。手机号、身份证号和邮箱按格式校验，空字符串表示清空，`null` 表示保留数据库原值。

类级别可使用 `@Validated` 校验路径参数和查询参数。

第一版重点校验：

- 注册：账号和密码不能为空，长度合理，邮箱格式正确。
- 登录：账号和密码不能为空。
- 普通用户修改资料：账号必须是4至32位的非空白字符串；手机号和邮箱只能修改为合法值，不能清空，传入 `null` 时保留原值；Service只定向更新这三个字段。
- 新建记录：题目不能为空且不超过50位，题材不能为空，标签不超过20位；不接收正文、状态和用户ID。记录修改时标签和正文传入 `null` 表示保留、空字符串表示清空，正文不能超过2000个字符。
- 对话：`huihuaId`、`command` 和编辑器当前正文不能为空，当前正文不能超过2000个字符；`command = 0` 时消息内容不能为空。
- 分页：当前列表接口尚未实现分页；后续增加分页时，页码和每页条数必须为正数并限制最大条数。

账号重复、数据归属等需要查数据库的规则属于Service业务校验，不写成注解。

## 5. 全局异常处理

建立业务异常和 `@RestControllerAdvice` 全局处理器，统一处理：

| 异常 | code | 说明 |
| --- | --- | --- |
| 参数校验异常 | 400 | 返回明确的第一个校验信息 |
| 请求体解析异常 | 400 | JSON格式错误或枚举值非法 |
| 业务异常 | 异常自带 | 账号重复、资源不存在、无权访问等 |
| 未登录 | 401 | 由拦截器返回 |
| 权限不足 | 403 | 由拦截器或业务检查返回 |
| 未知异常 | 500 | 学习联调阶段返回 `e.getMessage()` |

当前全局异常处理器已覆盖：

```text
MethodArgumentNotValidException
MethodArgumentTypeMismatchException
MissingServletRequestParameterException
ConstraintViolationException
BindException
HttpMessageNotReadableException
HttpRequestMethodNotSupportedException
HttpMediaTypeNotSupportedException
```

学习联调阶段未知异常允许返回 `e.getMessage()`，但不主动回显密码、Token或API Key。

## 6. 统一响应

所有Controller返回：

```java
Result<T>
```

状态码：

```text
200 成功
400 参数或业务请求错误
401 未登录
403 没有权限
404 数据不存在
500 服务端或AI调用失败
```

`Result`需要支持：

```java
Result.success()
Result.success(data)
Result.fail(code, message)
```

已被全局异常处理器处理的异常保持HTTP 200；前端统一判断 `Result.code`。

## 7. 创建时间和修改时间

当前项目不使用 `MetaObjectHandler` 或 `FieldFill`，而是由MySQL负责创建时间和修改时间。

`Jilu.chuangjianShijian` 和 `Jilu.xiugaiShijian` 均配置：

```java
insertStrategy = FieldStrategy.NEVER
updateStrategy = FieldStrategy.NEVER
```

因此MyBatis-Plus在插入和更新时都不会主动写入这两个字段，分别由数据库的 `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP` 维护。

实体使用标准 `LocalDateTime` 接收查询结果；`FieldStrategy.NEVER` 只控制插入和更新SQL，不影响数据库时间值回填后的查询映射。

`Huihua`当前没有时间字段，不为它额外设计自动填充；以后确有排序需求时再增加。

## 8. 密码和敏感字段

密码处理遵守：

- 注册时使用Hutool 5.8.12提供的BCrypt密码哈希后再保存。
- 登录时使用哈希校验，不能解密比较。
- 正式日志不应打印明文密码和密码哈希。当前开发配置启用了MyBatis标准输出日志，SQL参数仍可能包含密码哈希、消息和正文，这是已知待处理问题。
- 查询接口不返回 `mima`。

当前使用双重保护：

1. 用户接口使用不含 `mima` 的响应DTO。
2. `Yonghu.mima`使用 `@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)`，允许请求写入但禁止响应序列化。

注册、登录和管理员修改请求可以包含明文密码；管理员修改中的密码为空白时不更新。Service只对需要保存的新密码执行BCrypt哈希。实体和任何响应DTO都不能回传密码，管理员查询同样不能返回密码。

`shenfenzheng`属于敏感信息。第一版可以按需求返回给用户本人和管理员，但日志中不要完整输出；以后再按需要做脱敏。

## 9. 事务边界

适合事务：

- 用户注册。
- 记录新增、修改和删除。
- 用户确认候选正文后保存记录。

当前记录批量删除已经使用 `@Transactional(rollbackFor = Exception.class)`：先检查全部记录是否存在且属于当前用户，任意一条检查失败时不删除任何记录；全部通过后统一删除。

当前AI发送流程：

```text
同一会话在当前应用实例内串行执行
command=0独立提交：保存人类消息
command=1或2：不保存按钮操作
ChatMemory.get(huihuaId)：读取并转换最近20条历史消息
事务外：调用AI并解析结果
CONTINUE / WAIT / OVER：都只保存一条普通AI消息
用户确认候选：通过现有 /jilu/modify 更新正文并设置DRAFT
```

模型JSON由 `linggu.ai.AIResponseParser` 统一解析并校验。`ChatMemoryImpl` 只通过 `ChatMemory.get(huihuaId)` 为活动对话读取并转换最近20条历史；可见消息写入和失败补偿统一由 `XiaoxiService` 完成。当前不使用 `MessageChatMemoryAdvisor`，业务流程不调用 `ChatMemory.add()` 和 `clear()`，避免保存模型原始JSON或重复持久化。

AI调用、解析或后续保存失败时，补偿删除本次新增的人类消息；清理失败不会覆盖原始异常。

`OVER` 只生成候选正文，并通过 `XiaoxiService.xinjian()` 保存为普通AI消息。原 `baocunAIShengchengJieguo()` 及其更新记录的事务代码已经删除。

这样远程AI调用不占用数据库事务，用户确认前也不会覆盖数据库中的正文。

## 10. 配置范围

当前只需要：

- `Jilu` 时间字段的 `FieldStrategy.NEVER` 配置。
- Spring Data Redis和 `StringRedisTemplate`。
- MVC拦截器注册配置。
- 全局异常处理器。
- 必要的请求DTO和响应VO。

当前开发配置中仍有本地数据库字面量配置，并启用了MyBatis SQL参数标准输出。后续应改为环境变量，并在非本地环境关闭参数日志，避免配置和业务内容进入源码、控制台或采集日志。

当前已经接入Redis保存登录Token，尚未接入Spring Security、JWT或OAuth。Redis当前不承担通用业务缓存。
