# 接口设计

> 公共规则见 [后端公共机制](./4.后端公共机制.md)，技术版本见 [开发总览](./1.开发总览.md)。

## 1. 通用约定

基础地址：`http://localhost:8080`

JSON请求头：

```http
Content-Type: application/json
Accept: application/json
```

登录成功后，响应数据中直接返回32位无连字符Token：

```json
{
  "code": 200,
  "data": "550e8400e29b41d4a716446655440000",
  "message": "success"
}
```

后续需要登录的请求携带：

```http
Authorization: Bearer 550e8400e29b41d4a716446655440000
```

Token只用于查找Redis中保存的用户ID。拦截器再查询数据库取得最新权限；客户端不能直接提交用户ID或权限代替Token。

所有实体ID均由UUID去除连字符后生成，当前长度为32；数据库字段使用 `varchar(64)` 预留空间。

统一响应：

```json
{
  "code": 200,
  "data": null,
  "message": "success"
}
```

枚举在JSON中使用名称，例如 `RIJI`、`DRAFT`、`ADMIN`。

## 2. 请求与响应对象

用户写入接口使用独立DTO，避免接收不应由客户端提交的实体字段：

- 注册请求不能提交 `id` 和 `quanxian`。
- 管理员修改用户使用 `GuanliyuanXiugaiDTO`，目标ID使用请求体中的 `id`。
- `GuanliyuanXiugaiDTO.mima`为可选字段：空白时保留原密码，非空时必须为6至32位。
- 新建记录不能提交 `id`、`yonghuId`、状态和时间。
- 用户响应永远不包含 `mima`。
- 类名、字段名可用英文或拼音，只要JSON映射一致。

## 3. 用户接口

下表中的用户接口均已在当前 `YonghuController` 中实现。

| 方法 | 路径 | 功能 | 权限 |
| --- | --- | --- | --- |
| POST | `/yonghu/register` | 注册 | 无 |
| POST | `/yonghu/login` | 登录并返回Token | 无 |
| POST | `/yonghu/refresh` | 按剩余有效期返回原Token或轮换新Token | 登录 |
| POST | `/yonghu/logout` | 删除当前Token | 登录 |
| GET | `/yonghu/me` | 查看个人信息 | 登录 |
| PUT | `/yonghu/update` | 修改个人资料 | 登录 |
| PUT | `/yonghu/password` | 校验原密码并修改密码 | 登录 |

注册请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456",
  "dianhua": null,
  "shenfenzheng": null,
  "youxiang": "zhangsan@example.com"
}
```

规则：账号和密码必填；账号唯一；密码哈希后保存；权限固定为 `USER`。

登录请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456"
}
```

登录成功后，服务端在Redis中保存：

```text
login:{token} → yonghuId
```

Token有效期为4天。前端每次启动应用且本地存在Token时请求：

```http
POST /yonghu/refresh
Authorization: Bearer 当前Token
```

Token剩余时间大于5小时时，接口返回原Token；剩余时间小于等于5小时时，服务端删除旧Token、创建并返回新Token。前端不区分新旧，统一保存响应中的Token。普通业务请求只验证Token，不调用刷新接口；Token已经过期时刷新失败并要求重新登录。

个人资料修改当前允许提交账号、手机号和邮箱，不能修改ID、密码和权限。账号为必填项，必须是4至32位的非空白字符串；手机号和邮箱可以省略，省略时保留原值，提交时必须符合格式要求且不能使用空字符串清空。修改密码时，用户ID从Token提取，不由前端提交；当前接口通过查询参数 `mima1` 和 `mima2` 接收原密码与新密码。这是项目有意保留的接口设计，不改为JSON请求体。

## 4. 记录接口

本节接口已经在当前 `JiluController` 和 `JiluServiceImpl` 中实现。所有接口均从登录Token对应的请求属性取得当前用户ID，Service按“记录ID + 当前用户ID”检查数据归属。

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/jilu/xinjian` | 新建记录 |
| GET | `/jilu/chakanliebiao` | 查询当前用户的记录列表 |
| GET | `/jilu/chakan?id={id}` | 查询详情 |
| PUT | `/jilu/xiugai?id={id}` | 修改记录 |
| DELETE | `/jilu/shanchu?id={id}` | 删除记录 |
| DELETE | `/jilu/piliangshanchu` | 批量删除记录 |
| PUT | `/jilu/wancheng?id={id}` | 标记完成 |

新建请求：

```json
{
  "timu": "今天的旅行",
  "ticai": "RIJI",
  "biaoqian": "旅行"
}
```

新建时题目不能为空且不超过50位，题材不能为空，标签允许为 `null` 且不超过20位。请求不接收正文、状态和用户ID；系统设置ID、当前用户ID、`DRAFT`状态和时间，正文固定为空。

修改请求可以在记录创建后写入或调整正文：

```json
{
  "timu": "今天的旅行",
  "ticai": "RIJI",
  "biaoqian": "旅行",
  "zhengwen": "后续填写的正文"
}
```

修改请求中的正文允许为空，但长度不能超过2000个字符。

当前列表接口不接收查询参数，返回当前用户的全部记录，并按 `xiugaiShijian` 倒序排列。列表使用 `JiluLiebiaoVO`，不返回正文和所属用户ID，包含：

```text
id
timu
ticai
biaoqian
jiluZhuangtai
chuangjianShijian
xiugaiShijian
```

没有记录时返回空列表。题目、题材、标签、状态筛选和分页尚未实现，后续按需要扩展。

批量删除请求体直接提交记录ID数组：

```json
[
  "记录ID1",
  "记录ID2"
]
```

批量删除会先去除重复ID，再检查全部记录是否存在且属于当前用户。任意记录不存在或不属于当前用户时返回404，并通过事务保证不删除任何记录；全部检查通过后统一删除。

业务规则：

- 用户只能操作自己的记录。
- 已完成记录再次修改后恢复为 `DRAFT`。
- 正文为空时不允许标记完成。
- 单条和批量删除记录后，数据库级联删除其会话和消息。
- 创建记录不自动创建会话，也不调用AI。

## 5. 会话与消息接口

会话创建、会话查看、会话列表、AI对话消息发送和消息列表已经实现。`DuihuaController` 已注入并调用 `AIChatService`，因此AI对话已有可用的HTTP入口。

### 5.1 当前会话接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/huihua/xinjian?jiluId={jiluId}` | 为指定记录创建空会话 |
| GET | `/huihua/chakan?huihuaId={huihuaId}` | 查看单个会话 |
| GET | `/huihua/liebiao?jiluId={jiluId}` | 查看指定记录的全部会话 |
| DELETE | `/huihua/shanchu?huihuaId={huihuaId}` | 删除会话并级联删除该会话的全部消息 |

会话接口都从登录Token取得当前用户ID，并检查记录是否属于当前用户。创建会话时使用32位无连字符UUID生成会话ID，只保存 `Huihua`，不自动创建消息，也不调用AI；创建接口返回 `Result<String>`，响应数据是新生成的 `huihuaId`。列表没有数据时返回空列表。

会话不提供修改接口。删除会话前会检查所属记录归属；删除 `Huihua` 后由数据库外键级联删除该会话的全部 `Xiaoxi`，所属记录和其他会话不受影响。

### 5.2 对话和消息接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/duihua/chat` | 正常对话、补充提问或生成候选正文，返回 `DuihuaVO` |
| GET | `/duihua/getlist?huihuaId={huihuaId}` | 按序号查看会话消息 |
| GET | `/duihua/test` | 测试AI连接 |

发送接口统一接收 `DuihuaDTO`：

```json
{
  "huihuaId": "会话ID",
  "command": 0,
  "neirong": "请帮我看看这段正文还可以怎样改进。",
  "zhengwen": "编辑器中的当前正文，可以尚未保存。"
}
```

字段规则：

- `huihuaId` 必填。
- `command` 必填，只能是0、1或2。
- `zhengwen` 三个命令都必填、不能是空白字符串且不能超过2000个字符，只作为本次AI上下文，不自动保存。
- `neirong` 在 `command = 0` 时必填并保存为人类消息；`command = 1`、`2` 时可以为空。
- 原 `XiaoxiXinjianDTO` 已由 `DuihuaDTO` 替代并删除。

三个命令统一进入 `AIChatService.duihua()`，由Service内部完成命令分派和公共流程：

| command | Service | 行为 |
| --- | --- | --- |
| `0` | `duihua()` | 保存人类消息，由AI结合用户意图返回任意合法状态 |
| `1` | `duihua()` | 不保存按钮操作，强制AI补充提问，只接受 `CONTINUE` |
| `2` | `duihua()` | 不保存按钮操作，强制AI生成候选正文，只接受 `OVER` |

### 5.3 AI对话处理

目标处理顺序：

1. 检查 `huihuaId` 对应会话和记录属于当前用户。
2. 检查 `command` 合法，并检查编辑器当前 `zhengwen` 非空且不超过2000个字符。
3. `command = 0` 保存非空 `neirong`；按钮命令不保存伪造的人类消息。
4. 查询记录题目、题材、标签和本会话完整历史。
5. 使用 `DuihuaDTO.zhengwen` 作为当前正文，不使用可能已经过期的数据库正文。
6. 不统计回合数，由AI根据用户意图、正文和历史决定处理方式。
7. 严格解析 `AIChatResponse` 的三个字段并校验字段组合。
8. 将AI回答保存为普通消息并返回 `DuihuaVO`。
9. `OVER` 的 `quanwen` 只作为候选正文返回和保存，不直接更新 `Jilu.zhengwen`。

状态协议以 `DuihuaZhuangtai` 为准：

```java
OVER(0),
CONTINUE(1),
WAIT(2);
```

- `CONTINUE`：继续交流或提出问题。
- `WAIT`：AI建议用户选择下一步，但不限制任何命令。
- `OVER`：本次生成了候选正文，不表示会话关闭。
- 用户明确要求生成时，普通 `duihua()` 应返回 `OVER`；用户明确要求暂不生成时不得返回 `OVER`；没有明确倾向时AI可以自主选择。
- AI可以根据上下文自行判断总结、扩写或润色，但不能编造重要事实。

响应：

```java
DuihuaVO
- Xiaoxi renleiXiaoxi
- Xiaoxi aiHuida
- DuihuaZhuangtai zhuangtai
```

- `command = 0` 成功时两个消息字段都非空。
- `command = 1`、`2` 没有新的人类消息，因此 `renleiXiaoxi = null`。
- 前端收到 `OVER` 后临时把 `aiHuida` 标记为候选正文。
- 用户点击使用后，候选正文进入编辑器；用户可以修改或直接确认。
- 确认时调用现有 `/jilu/xiugai` 保存，不新增后端候选确认接口。
- 后续对话继续提交编辑器当前正文，因此AI可以读取尚未保存的修改。
- 刷新后临时候选标记和未保存正文可以丢失，但候选文字仍保留在普通消息历史中。

## 6. 管理员接口

管理员方法已从 `YonghuController` 提取到 `GuanliyuanController`，类级路径为 `/admin`。当前接口为：

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/admin/add` | 新建用户 |
| GET | `/admin/get?yonghuId={id}` | 查询用户详情 |
| GET | `/admin/getlist` | 查询用户列表 |
| PUT | `/admin/modify` | 修改用户信息，使用 `GuanliyuanXiugaiDTO`，密码可选 |
| DELETE | `/admin/delete?id={id}` | 删除用户 |

类级路径 `/admin` 及其子路径全部要求当前Token对应的权限为 `ADMIN`。任何响应都不返回密码或密码哈希。

当前用户列表一次返回全部用户，不支持模糊查询和分页。列表与详情都返回用户ID，供前端执行详情查询、修改和删除。

管理员新建用户时可以指定权限，密码经BCrypt哈希后保存。管理员修改使用 `GuanliyuanXiugaiDTO` 接收ID、账号、可选密码、手机号、身份证号、邮箱和权限：ID、账号和权限必填；非空密码必须为6至32位并在Service中加密；密码为 `null`、空字符串或纯空白时保留原密码。手机号、身份证号和邮箱按格式校验，可以使用空字符串清空；传入 `null` 时保留数据库原值，不将字段恢复为数据库 `NULL`。


## 7. 错误约定

已被全局异常处理器处理的错误保持HTTP 200，实际结果由统一响应体中的 `code` 表示：

```text
400 参数或业务请求错误
401 未登录
403 没有权限
404 数据不存在
500 服务端或AI调用失败
```

资源归属检查可以对“其他用户的数据”统一返回404，减少资源信息泄露；项目选定后保持一致。
