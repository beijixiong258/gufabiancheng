# 接口设计

> 公共规则见 [后端公共机制](./4.后端公共机制.md)，技术版本见 [开发总览](./1.开发总览.md)。

## 1. 通用约定

基础地址：`http://localhost:8080`

JSON请求头：

```http
Content-Type: application/json
Accept: application/json
```

登录成功后，响应数据中直接返回32位无连字符Token：

```json
{
  "code": 200,
  "data": "550e8400e29b41d4a716446655440000",
  "message": "success"
}
```

后续需要登录的请求携带：

```http
Authorization: Bearer 550e8400e29b41d4a716446655440000
```

Token只用于查找Redis中保存的用户ID。拦截器再查询数据库取得最新权限；客户端不能直接提交用户ID或权限代替Token。

所有实体ID均由UUID去除连字符后生成，当前长度为32；数据库字段使用 `varchar(64)` 预留空间。

统一响应：

```json
{
  "code": 200,
  "data": null,
  "message": "success"
}
```

枚举在JSON中使用名称，例如 `RIJI`、`DRAFT`、`ADMIN`。

## 2. 请求与响应对象

普通用户请求主要使用DTO，避免接收不应由前端提交的字段；管理员全量修改用户时按当前实现直接接收 `Yonghu` 实体：

- 注册请求不能提交 `id` 和 `quanxian`。
- 管理员修改用户时，目标ID直接使用请求体中的 `Yonghu.id`。
- `Yonghu.mima`为只写JSON字段：请求可以提交新密码，响应不会返回密码。
- 新建记录不能提交 `id`、`yonghuId`、状态和时间。
- 用户响应永远不包含 `mima`。
- 类名、字段名可用英文或拼音，只要JSON映射一致。

## 3. 用户接口

下表中的用户接口均已在当前 `YonghuController` 中实现。

| 方法 | 路径 | 功能 | 权限 |
| --- | --- | --- | --- |
| POST | `/yonghu/register` | 注册 | 无 |
| POST | `/yonghu/login` | 登录并返回Token | 无 |
| POST | `/yonghu/refresh` | 按剩余有效期返回原Token或轮换新Token | 登录 |
| POST | `/yonghu/logout` | 删除当前Token | 登录 |
| GET | `/yonghu/me` | 查看个人信息 | 登录 |
| PUT | `/yonghu/update` | 修改个人资料 | 登录 |
| PUT | `/yonghu/password` | 校验原密码并修改密码 | 登录 |

注册请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456",
  "dianhua": null,
  "shenfenzheng": null,
  "youxiang": "zhangsan@example.com"
}
```

规则：账号和密码必填；账号唯一；密码哈希后保存；权限固定为 `USER`。

登录请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456"
}
```

登录成功后，服务端在Redis中保存：

```text
login:{token} → yonghuId
```

Token有效期为4天。前端每次启动应用且本地存在Token时请求：

```http
POST /yonghu/refresh
Authorization: Bearer 当前Token
```

Token剩余时间大于5小时时，接口返回原Token；剩余时间小于等于5小时时，服务端删除旧Token、创建并返回新Token。前端不区分新旧，统一保存响应中的Token。普通业务请求只验证Token，不调用刷新接口；Token已经过期时刷新失败并要求重新登录。

个人资料修改当前允许提交账号、手机号和邮箱，不能修改ID、密码和权限。账号为必填项，必须是4至32位的非空白字符串；手机号和邮箱可以省略，省略时保留原值，提交时必须符合格式要求且不能使用空字符串清空。修改密码时，用户ID从Token提取，不由前端提交。

## 4. 记录接口

本节接口已经在当前 `JiluController` 和 `JiluServiceImpl` 中实现。所有接口均从登录Token对应的请求属性取得当前用户ID，Service按“记录ID + 当前用户ID”检查数据归属。

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/jilu/xinjian` | 新建记录 |
| GET | `/jilu/chakanliebiao` | 查询当前用户的记录列表 |
| GET | `/jilu/chakan?id={id}` | 查询详情 |
| PUT | `/jilu/xiugai?id={id}` | 修改记录 |
| DELETE | `/jilu/shanchu?id={id}` | 删除记录 |
| DELETE | `/jilu/piliangshanchu` | 批量删除记录 |
| PUT | `/jilu/wancheng?id={id}` | 标记完成 |

新建请求：

```json
{
  "timu": "今天的旅行",
  "ticai": "RIJI",
  "biaoqian": "旅行"
}
```

新建时题目不能为空且不超过50位，题材不能为空，标签允许为 `null` 且不超过20位。请求不接收正文、状态和用户ID；系统设置ID、当前用户ID、`DRAFT`状态和时间，正文固定为空。

修改请求可以在记录创建后写入或调整正文：

```json
{
  "timu": "今天的旅行",
  "ticai": "RIJI",
  "biaoqian": "旅行",
  "zhengwen": "后续填写的正文"
}
```

当前列表接口不接收查询参数，返回当前用户的全部记录，并按 `xiugaiShijian` 倒序排列。列表使用 `JiluLiebiaoVO`，不返回正文和所属用户ID，包含：

```text
id
timu
ticai
biaoqian
zhuangtai
chuangjianShijian
xiugaiShijian
```

没有记录时返回空列表。题目、题材、标签、状态筛选和分页尚未实现，后续按需要扩展。

批量删除请求体直接提交记录ID数组：

```json
[
  "记录ID1",
  "记录ID2"
]
```

批量删除会先去除重复ID，再检查全部记录是否存在且属于当前用户。任意记录不存在或不属于当前用户时返回404，并通过事务保证不删除任何记录；全部检查通过后统一删除。

业务规则：

- 用户只能操作自己的记录。
- 已完成记录再次修改后恢复为 `DRAFT`。
- 正文为空时不允许标记完成。
- 单条和批量删除记录后，数据库级联删除其会话和消息。
- 创建记录不自动创建会话，也不调用AI。

## 5. 会话与消息接口

会话创建、会话查看、会话列表、用户消息新建和消息列表已经实现。`AIChatService.duihua()` 已完成AI对话业务编排，但当前尚未由 `XiaoxiController` 调用，因此AI对话还没有可用的HTTP入口。

### 5.1 当前会话接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/huihua/xinjian?jiluId={jiluId}` | 为指定记录创建空会话 |
| GET | `/huihua/chakan?huihuaId={huihuaId}` | 查看单个会话 |
| GET | `/huihua/liebiao?jiluId={jiluId}` | 查看指定记录的全部会话 |

会话接口都从登录Token取得当前用户ID，并检查记录是否属于当前用户。创建会话时使用32位无连字符UUID生成会话ID，只保存 `Huihua`，不自动创建消息，也不调用AI；创建接口返回 `Result<String>`，响应数据是新生成的 `huihuaId`。列表没有数据时返回空列表。

会话创建后不提供修改接口。第一版也暂未设计会话删除接口。

### 5.2 当前消息接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/xiaoxi/xinjian?huihuaId={huihuaId}` | 当前只保存一条用户消息 |
| GET | `/xiaoxi/chakanliebiao?huihuaId={huihuaId}` | 按序号查看会话消息 |

发送用户消息请求：

```json
{
  "neirong": "当时天气很冷，我印象最深的是河边的老房子。"
}
```

当前消息处理规则：

1. Controller只接收消息内容，固定以 `laiyuan = 1` 调用Service，前端不能伪造AI消息。
2. Service检查消息来源只能是0或1，并检查“会话 → 记录 → 当前用户”的归属关系。
3. 消息内容不能为空。
4. 新消息 `xuhao` 为当前会话最大序号加1，第一条消息从1开始。
5. 新消息使用32位无连字符UUID作为ID，保存成功后重新查询并返回包含数据库生成时间的完整消息。
6. 消息列表只查询指定会话，并按 `xuhao` 升序返回；没有消息时返回空列表。
7. `laiyuan = 1` 表示用户，`laiyuan = 0` 表示AI回复。

### 5.3 当前AI对话Service

`AIChatService.duihua(yonghuId, huihuaId, neirong)` 当前处理顺序：

1. 检查会话和记录归属。
2. 以 `laiyuan = 1` 保存本轮用户消息。
3. 查询记录和包含本轮用户消息的完整会话历史。
4. 按 `SystemMessage`、`UserMessage`、`AssistantMessage` 组装上下文。
5. 调用Spring AI，并把模型JSON解析为 `AIChatResponse`。
6. 校验 `zhuangtai`、`yindao` 和 `quanwen` 的组合。
7. 以 `laiyuan = 0` 保存AI回复。
8. 状态为1时，在同一个短事务中保存AI回复、更新 `Jilu.zhengwen` 并将记录恢复为 `DRAFT`。

模型内部返回协议：

```json
{
  "zhuangtai": 0,
  "yindao": "这件事发生在哪里？",
  "quanwen": null
}
```

或者：

```json
{
  "zhuangtai": 1,
  "yindao": null,
  "quanwen": "完整正文"
}
```

- `zhuangtai = 0`：保存 `yindao` 为AI回复，不修改正文。
- `zhuangtai = 1`：保存 `quanwen` 为AI回复，同时用它更新记录正文。
- 前端不接收 `AIChatResponse`，只接收持久化后的 `Xiaoxi`，通过 `laiyuan` 判断消息来源。
- AI调用、解析或校验失败时保留用户消息，不保存AI回复，不修改正文。

当前剩余工作是让 `XiaoxiController` 注入并调用 `AIChatService`；在此之前，`POST /xiaoxi/xinjian` 仍只保存用户消息，不会触发AI。

## 6. 管理员接口

管理员方法已从 `YonghuController` 提取到 `GuanliyuanController`，类级路径为 `/admin`。当前接口为：

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/admin/add` | 新建用户 |
| GET | `/admin/get?yonghuId={id}` | 查询用户详情 |
| GET | `/admin/getlist` | 查询用户列表 |
| PUT | `/admin/modify` | 全量修改用户信息，请求体包含目标用户ID |
| DELETE | `/admin/delete?id={id}` | 删除用户 |

类级路径 `/admin` 及其子路径全部要求当前Token对应的权限为 `ADMIN`。任何响应都不返回密码或密码哈希。

当前用户列表一次返回全部用户，不支持模糊查询和分页。列表与详情都返回用户ID，供前端执行详情查询、修改和删除。

管理员新建用户时可以指定权限，密码经BCrypt哈希后保存。管理员全量修改直接接收ID、账号、密码、手机号、身份证号、邮箱和权限；请求体中的ID是修改目标。密码为空时按当前Service实现重置为默认密码，随后保存其BCrypt哈希。手机号、身份证号和邮箱可以设置为空字符串；传入 `null` 时MyBatis-Plus不更新原值，不将字段恢复为数据库 `NULL`。

记录模块开发后，管理员还可以按记录ID删除任意用户的一条记录；该方法放入 `GuanliyuanController`，方法级HTTP路径由用户编写，删除记录时由数据库级联删除对应会话和消息。

## 7. 错误约定

已被全局异常处理器处理的错误保持HTTP 200，实际结果由统一响应体中的 `code` 表示：

```text
400 参数或业务请求错误
401 未登录
403 没有权限
404 数据不存在
500 服务端或AI调用失败
```

资源归属检查可以对“其他用户的数据”统一返回404，减少资源信息泄露；项目选定后保持一致。
