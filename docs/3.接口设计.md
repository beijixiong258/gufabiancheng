# 接口设计

> 公共规则见 [后端公共机制](./4.后端公共机制.md)，技术版本见 [开发总览](./1.开发总览.md)。

## 1. 通用约定

基础地址：`http://localhost:8080`

JSON请求头：

```http
Content-Type: application/json
Accept: application/json
```

登录成功后，响应数据中直接返回32位无连字符Token：

```json
{
  "code": 200,
  "data": "550e8400e29b41d4a716446655440000",
  "message": "success"
}
```

后续需要登录的请求携带：

```http
Authorization: Bearer 550e8400e29b41d4a716446655440000
```

Token只用于查找Redis中保存的用户ID。拦截器再查询数据库取得最新权限；客户端不能直接提交用户ID或权限代替Token。

所有实体ID均由UUID去除连字符后生成，当前长度为32；数据库字段使用 `varchar(64)` 预留空间。

统一响应：

```json
{
  "code": 200,
  "data": null,
  "message": "success"
}
```

枚举在JSON中使用名称，例如 `RIJI`、`DRAFT`、`ADMIN`。

## 2. 请求与响应对象

接口使用简单DTO，避免直接暴露完整实体：

- 注册请求不能提交 `id` 和 `quanxian`。
- 新建记录不能提交 `id`、`yonghuId`、状态和时间。
- 用户响应永远不包含 `mima`。
- 类名、字段名可用英文或拼音，只要JSON映射一致。

## 3. 用户接口

下表是用户模块的目标接口。当前 `YonghuController` 已实现注册、登录、刷新Token和修改密码；退出登录、查看资料、更新资料及管理员接口仍待开发。

| 方法 | 路径 | 功能 | 权限 |
| --- | --- | --- | --- |
| POST | `/yonghu/zhuce` | 注册 | 无 |
| POST | `/yonghu/denglu` | 登录并返回Token | 无 |
| POST | `/yonghu/shuaxin` | 按剩余有效期返回原Token或轮换新Token | 登录 |
| POST | `/yonghu/tuichu` | 删除当前Token | 登录 |
| GET | `/yonghu/chakan` | 查看个人信息 | 登录 |
| PUT | `/yonghu/gengxin` | 修改个人资料 | 登录 |
| PUT | `/yonghu/mima` | 校验原密码并修改密码 | 登录 |

注册请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456",
  "dianhua": null,
  "shenfenzheng": null,
  "youxiang": "zhangsan@example.com"
}
```

规则：账号和密码必填；账号唯一；密码哈希后保存；权限固定为 `USER`。

登录请求：

```json
{
  "zhanghao": "zhangsan",
  "mima": "123456"
}
```

登录成功后，服务端在Redis中保存：

```text
login:{token} → yonghuId
```

Token有效期为4天。前端每次启动应用且本地存在Token时请求：

```http
POST /yonghu/shuaxin
Authorization: Bearer 当前Token
```

Token剩余时间大于5小时时，接口返回原Token；剩余时间小于等于5小时时，服务端删除旧Token、创建并返回新Token。前端不区分新旧，统一保存响应中的Token。普通业务请求只验证Token，不调用刷新接口；Token已经过期时刷新失败并要求重新登录。

个人资料修改当前允许提交账号、手机号和邮箱，不能修改ID、密码和权限。修改密码时，用户ID从Token提取，不由前端提交。

## 4. 记录接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/jilu` | 新建记录 |
| GET | `/jilu` | 查询当前用户记录 |
| GET | `/jilu/{id}` | 查询详情 |
| PUT | `/jilu/{id}` | 修改记录 |
| DELETE | `/jilu/{id}` | 删除记录 |
| PUT | `/jilu/{id}/wancheng` | 标记完成 |

新建或修改请求：

```json
{
  "timu": "今天的旅行",
  "ticai": "RIJI",
  "biaoqian": "旅行",
  "zhengwen": "初始正文"
}
```

`biaoqian`和`zhengwen`允许为 `null`。新建时系统设置ID、用户ID、`DRAFT`状态和时间。

列表查询参数：

```text
timu       题目模糊查询
ticai      题材精确查询
biaoqian   标签精确查询
zhuangtai  状态精确查询
dangqian   页码，默认1
daxiao     每页数量，默认10并限制最大值
```

所有查询必须包含当前用户ID，默认按修改时间倒序。

业务规则：

- 用户只能操作自己的记录。
- 已完成记录再次修改后恢复为 `DRAFT`。
- 正文为空时不允许标记完成。
- 删除记录后数据库级联删除会话和消息。
- 创建记录不自动创建会话，也不调用AI。

## 5. 会话与消息接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/jilu/{jiluId}/huihua` | 创建空会话 |
| GET | `/jilu/{jiluId}/huihua` | 查询记录的会话 |
| GET | `/huihua/{huihuaId}/xiaoxi` | 按序号查询消息 |
| POST | `/huihua/{huihuaId}/xiaoxi` | 发送消息并调用AI |

创建会话时只保存 `Huihua`，不自动调用AI。

发送消息请求：

```json
{
  "neirong": "当时天气很冷，我印象最深的是河边的老房子。"
}
```

处理顺序：

1. 检查会话、记录和当前用户的归属关系。
2. 保存用户消息。
3. 查询记录和本会话历史。
4. 调用Spring AI并解析结构化结果。
5. 保存AI消息。
6. 返回正文时更新记录正文和修改时间。

响应数据：

```json
{
  "leixing": "ZHUIWEN",
  "xiaoxi": {
    "huihuaId": "会话ID",
    "neirong": "这件事发生在哪里？",
    "laiyuan": 0,
    "xuhao": 1
  },
  "zhengwen": null
}
```

`leixing`取值：

- `ZHUIWEN`：保存AI问题，不修改正文。
- `ZHENGWEN`：保存AI回复，并用非空 `zhengwen` 更新记录。

AI失败时保留用户消息，不保存空AI消息，不修改正文。

## 6. 管理员接口

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| GET | `/yonghu/admin` | 查询用户列表 |
| POST | `/yonghu/admin` | 新增用户 |
| GET | `/yonghu/admin/{id}` | 查询用户详情 |
| PUT | `/yonghu/admin/{id}` | 全量修改用户信息 |
| DELETE | `/yonghu/admin/{id}` | 删除用户 |

全部要求当前Token对应的权限为 `ADMIN`。任何响应都不返回密码或密码哈希；管理员暂不提供密码重置功能。

用户列表支持账号模糊查询和分页。第一版建议禁止管理员删除当前登录的自己。

## 7. 错误约定

已被全局异常处理器处理的错误保持HTTP 200，实际结果由统一响应体中的 `code` 表示：

```text
400 参数或业务请求错误
401 未登录
403 没有权限
404 数据不存在
500 服务端或AI调用失败
```

资源归属检查可以对“其他用户的数据”统一返回404，减少资源信息泄露；项目选定后保持一致。
