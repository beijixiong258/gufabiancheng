# HTTP状态码使用说明

> 本文用于判断接口成功或失败时应该返回哪个HTTP状态码。项目接口约定见 [接口设计](./3.接口设计.md)，异常处理见 [后端公共机制](./4.后端公共机制.md)。

## 1. 先区分两种code

一次接口响应中可能同时存在：

1. **HTTP状态码**：位于HTTP响应行中，由浏览器、Postman和前端请求库直接识别。
2. **响应体中的 `code`**：位于项目统一返回的JSON中，方便前端按统一格式处理。

本项目保持二者一致：

```http
HTTP/1.1 404 Not Found
Content-Type: application/json
```

```json
{
  "code": 404,
  "data": null,
  "message": "记录不存在"
}
```

不要出现HTTP状态码为 `200`，但响应体 `code` 为 `404` 的情况，否则前端、日志和监控容易产生歧义。

## 2. 本项目常用状态码

| 状态码 | 含义 | 什么时候使用 | 本项目示例 |
| --- | --- | --- | --- |
| `200 OK` | 请求成功 | 查询、创建、修改、删除成功 | 登录成功、创建记录成功、删除记录成功 |
| `400 Bad Request` | 请求内容不符合接口要求 | 参数为空、格式错误、枚举值错误、违反普通业务规则 | 账号或密码为空、正文为空却要求完成记录 |
| `401 Unauthorized` | 未登录或登录凭证无效 | 未提供Token，或者Token不存在、已退出、已失效 | 请求个人信息时没有有效的 `X-Token` |
| `403 Forbidden` | 已登录，但没有操作权限 | 身份已经确认，但权限不足 | 普通用户访问管理员接口 |
| `404 Not Found` | 请求的资源不存在 | 根据ID找不到数据；或者为了避免泄露而隐藏其他用户的数据 | 记录ID不存在、访问不属于自己的记录 |
| `500 Internal Server Error` | 服务端发生未知错误 | 程序缺陷、未预料异常、数据库或AI调用失败且没有更合适的状态码 | 空指针异常、数据库异常、AI服务调用异常 |

第一版优先使用以上六种，不必为了完整而引入过多状态码。

## 3. 最容易混淆的情况

### 3.1 400和404

判断关键：错误来自“请求内容不合理”，还是“目标资源不存在”。

```text
题目为空                         → 400
UUID格式错误                     → 400
记录ID格式正确，但数据库中不存在  → 404
正文为空却要求标记完成            → 400
```

### 3.2 401和403

判断关键：服务端是否已经确认当前用户是谁。

```text
没有Token                         → 401
Token不存在或已经退出              → 401
已登录普通用户访问管理员接口        → 403
已登录用户访问其他用户的记录        → 本项目统一返回404
```

口诀：

```text
401：你是谁？
403：知道你是谁，但你不能做。
```

### 3.3 400和500

判断关键：问题是否由客户端修改请求后即可解决。

```text
前端漏传必填字段                  → 400
前端传入不存在的枚举名称           → 400
账号重复                          → 400
数据库连接失败                    → 500
代码抛出未处理异常                 → 500
AI服务调用失败                    → 500
```

不能因为Service抛出了异常就一律返回500。可预料的参数和业务错误属于客户端请求问题，通常返回400；只有服务端自己出错时才返回500。

## 4. 按处理阶段选择状态码

可以按以下顺序判断：

```text
请求是否成功？
├─ 是 → 200
└─ 否
   ├─ Token缺失或无效？ → 401
   ├─ 已登录但权限不足？ → 403
   ├─ 目标资源不存在？ → 404
   ├─ 参数或普通业务规则不满足？ → 400
   └─ 服务端发生未预料错误？ → 500
```

在记录、会话和消息接口中，应先完成登录检查，再检查资源是否存在及是否属于当前用户。

## 5. 常见接口示例

| 场景 | 返回状态码 |
| --- | --- |
| 注册成功 | `200` |
| 账号已存在 | `400` |
| 登录成功 | `200` |
| 账号或密码错误 | `400` |
| 未携带 `X-Token` | `401` |
| 普通用户访问 `/guanliyuan/**` | `403` |
| 查询不存在的记录 | `404` |
| 查询其他用户的记录 | `404` |
| 新建记录时题目为空 | `400` |
| AI调用失败 | `500` |
| 删除记录成功 | `200` |

## 6. 为什么暂时不用其他状态码

HTTP还定义了 `201`、`204`、`409`、`422`、`429`、`502`、`503` 等状态码。例如，资源创建成功可以返回 `201 Created`，账号冲突可以返回 `409 Conflict`。

这些状态码并不是错误，但本项目是学习阶段的简单统一响应设计。为了减少Controller和前端判断分支，第一版统一采用：

```text
成功：200
客户端请求问题：400、401、403、404
服务端问题：500
```

以后进入更严格的REST API设计阶段，再根据实际需求细分状态码。

## 7. 与CommonException的关系

可预料的业务错误统一抛出带 `code` 和 `message` 的 `CommonException`：

```text
账号已经存在              → CommonException(400, "账号已经存在")
记录不存在                → CommonException(404, "记录不存在")
当前用户没有管理员权限      → CommonException(403, "没有管理员权限")
```

`GlobalExceptionHandler`读取异常中的 `code`：

1. 将它设置为HTTP状态码。
2. 同时写入统一响应体的 `code`。
3. 将异常中的 `message` 写入响应体。

未知异常不转换成400，应由兜底处理返回500。学习阶段可以直接将 `e.getMessage()` 放入响应体，方便前端联调，但不能返回完整堆栈、密码、Token或API Key。
