# 人工智能对话逻辑设计

> 技术版本见 [开发总览](./1.开发总览.md)，接口状态见 [接口设计](./3.接口设计.md)。

## 1. 目标

AI以用户已经写出的正文为基础，结合题目、题材、标签和本会话历史进行追问、总结、扩写或润色。

设计原则：

- 用户可以创建正文为空的草稿，但调用AI时，编辑器当前正文必须非空且不超过2000个字符。
- 不使用固定问答轮数，不建立强制会话状态机。
- AI根据用户意图和上下文决定继续交流、等待选择或生成候选正文。
- 用户可以在任意阶段要求生成，例如第二轮就要求总结。
- AI也可以在用户没有明确要求时，根据内容完整度主动生成候选正文。
- 用户明确要求继续交流或暂不生成时，AI不得生成候选正文。
- AI不得编造用户没有提供的重要事实。

第一版使用Spring AI `ChatClient` 同步取得完整结果，不做流式输出。

## 2. 数据职责

```text
Jilu               保存用户已经确认的题目、题材、标签、正文和完成状态
Huihua             表示围绕一条记录进行的一次对话，不保存对话状态
Xiaoxi             保存用户和AI的每条可见消息，不区分普通回复和候选正文
DuihuaDTO           保存一次对话请求和编辑器当前正文
AIChatResponse     仅用于后端解析模型JSON
DuihuaVO            返回本次人类消息、AI回答和本次对话状态
DuihuaZhuangtai     表示本次AI处理结果，不是持久化的会话状态
```

一条记录可以创建多个会话。每次AI请求只使用本会话的 `Xiaoxi` 作为历史，同时使用 `DuihuaDTO.zhengwen` 作为当前正文。该正文可以是编辑器中尚未保存的内容。

消息来源根据 `Xiaoxi.laiyuan` 判断：

```text
laiyuan = 1 → 用户消息
laiyuan = 0 → AI回复
```

## 3. 对话入口和请求DTO

当前对话入口：

```http
POST /duihua/chat
Content-Type: application/json
```

请求体统一使用：

```java
DuihuaDTO
- String huihuaId
- Integer command
- String neirong
- String zhengwen
```

示例：

```json
{
  "huihuaId": "会话ID",
  "command": 0,
  "neirong": "请帮我看看这段正文还可以怎样改进。",
  "zhengwen": "编辑器中的当前正文，可以尚未保存。"
}
```

字段规则：

- `huihuaId` 必填，用于检查会话归属并查询本会话历史。
- `command` 必填，只能是0、1或2。
- `zhengwen` 三个命令都必填且不能是空白字符串，只作为本次AI上下文，不自动保存。
- `neirong` 仅在 `command = 0` 时必填并保存为人类消息；按钮命令不保存伪造的人类消息。
- `yonghuId` 从登录Token取得，不能由前端提交。
- `jiluId` 通过 `huihuaId` 查询，不能由前端指定。

原 `XiaoxiXinjianDTO` 已由 `DuihuaDTO` 完全替代并删除。

## 4. 单一Service入口和三个命令

Controller不再分派三个Service方法，统一调用：

```java
AIChatService.duihua(String yonghuId, DuihuaDTO duihuaDTO)
```

`duihua()` 内部集中完成：

1. 校验 `command`，并在命令0时检查 `neirong` 非空。
2. 查询会话、记录和本会话历史。
3. 只有命令0保存人类消息。
4. 根据命令选择普通对话、补充或结束指令。
5. 调用AI并解析结果。
6. 根据命令校验返回状态。
7. 保存AI回复并构造统一的 `DuihuaVO`。

### 4.1 `command = 0`

- 保存非空的 `neirong` 为人类消息。
- AI根据当前正文、历史和用户意图返回 `CONTINUE`、`WAIT` 或 `OVER`。
- 用户明确要求生成、总结、扩写或润色时，应返回 `OVER`。
- 用户明确要求继续讨论或暂不生成时，不得返回 `OVER`。
- 用户没有明确表达倾向时，AI可以自主选择三种状态。

### 4.2 `command = 1`

- 不保存按钮操作为人类消息。
- 强制AI只补充提问一个新的、有价值且不重复的问题。
- 只接受 `CONTINUE`。

### 4.3 `command = 2`

- 不保存按钮操作为人类消息。
- 强制AI根据当前正文和历史生成候选正文。
- 只接受 `OVER`。

三个命令都可以随时调用，不依赖此前是否出现过 `WAIT` 或 `OVER`。`OVER` 后用户仍可继续发送新想法。

## 5. 对话状态语义

状态枚举改名为 `DuihuaZhuangtai`：

```java
OVER(0),
CONTINUE(1),
WAIT(2);
```

含义：

- `CONTINUE`：本次回复继续交流或提出问题。
- `WAIT`：AI认为可以生成，但倾向先询问用户如何处理。
- `OVER`：本次生成完成并返回候选正文，不代表会话关闭。

状态只随本次 `DuihuaVO` 返回，不写入 `Huihua` 或 `Xiaoxi`。刷新页面后不恢复候选标记或精确状态，这是第一版主动接受的简化。

## 6. AI上下文和提示词

每次调用AI时组装：

```text
SystemMessage
├─ 固定AI行为和安全要求
├─ 本次命令要求
├─ 记录题目
├─ 记录题材
├─ 记录标签
└─ DuihuaDTO.zhengwen中的编辑器当前正文

历史消息
├─ laiyuan=1 → UserMessage
└─ laiyuan=0 → AssistantMessage
```

正文来自请求DTO，不直接使用数据库中可能已经过期的 `Jilu.zhengwen`。正文只作为资料，用户在 `neirong` 中表达的当前意图用于指导本次操作。

取消以下逻辑：

- `huiheTongji()` 回合数统计。
- `huoquTishici()` 按回合数选择提示词。
- `duihuaZhuangtaiJiaoyan()` 按5至8轮限制状态。
- `JIXU`、`ZHUIWEN`、`SHENGCHENG` 三个固定回合提示词。

保留并调整普通对话、补充和结束三种命令提示。AI在用户未指定时可以自行判断总结、扩写或润色；判断不清时可以返回 `WAIT` 询问用户。

## 7. 模型JSON协议和安全围栏

模型结果解析为：

```java
AIChatResponse
- Integer zhuangtai
- String yindao
- String quanwen
```

`CONTINUE(1)`：

```json
{
  "zhuangtai": 1,
  "yindao": "普通回复或一个需要继续确认的问题",
  "quanwen": null
}
```

`WAIT(2)`：

```json
{
  "zhuangtai": 2,
  "yindao": "正文已经可以进一步处理，你希望我总结、扩写还是润色？",
  "quanwen": null
}
```

`OVER(0)`：

```json
{
  "zhuangtai": 0,
  "yindao": null,
  "quanwen": "本次生成的候选正文"
}
```

后端只执行可确定的安全校验：

- 请求中的当前正文必须非空且不超过2000个字符。
- JSON对象必须恰好包含 `zhuangtai`、`yindao`、`quanwen` 三个字段。
- 检查重复字段、字段类型和字段组合。
- `OVER` 要求 `yindao` 为空且 `quanwen` 非空。
- `CONTINUE` 和 `WAIT` 要求 `yindao` 非空且 `quanwen` 为空。
- 命令1只接受 `CONTINUE`。
- 命令2只接受 `OVER`。
- `duihua()` 不按回合数限制状态。

“是否应该总结、扩写或润色”属于主观意图，由提示词和模型判断，不由后端硬编码校验。

## 8. 候选正文和编辑器

`OVER` 的 `quanwen` 只作为普通AI消息保存，不立即更新 `Jilu.zhengwen`。提示词要求候选正文不超过2000个字符。

前端处理流程：

```text
收到 DuihuaVO.zhuangtai = OVER
        ↓
临时把 aiHuida 标记为候选正文
        ↓
用户点击“使用此版本”
        ↓
候选正文放入编辑器，不立即写数据库
        ↓
用户继续修改或直接确认
        ↓
调用现有 /jilu/xiugai 保存
```

约定：

- 不新增候选正文表、消息类型字段或后端确认接口。
- 用户未确认前，数据库中的正文保持不变。
- 候选进入编辑器后，每次AI请求继续携带编辑器当前正文，因此AI能够看到尚未保存的修改。
- 刷新页面后，前端临时候选标记和未保存正文可以丢失；候选文字仍作为普通AI消息保留在历史中。
- 用户确认保存后，记录状态恢复为 `DRAFT`；之后仍由用户主动调用完成接口改为 `FINISH`。

## 9. 事务和失败处理

目标事务边界：

```text
command=0：独立保存人类消息
command=1或2：不保存按钮操作
事务外：调用AI并解析结果
CONTINUE / WAIT / OVER：都只保存一条普通AI消息
用户确认候选：通过现有记录修改接口保存正文并设置DRAFT
```

AI生成候选正文和更新记录正文不再处于同一事务，因为AI生成阶段不修改记录。

AI调用、JSON解析或业务校验失败时：

- 已保存的用户消息保留。
- 不保存空AI回复。
- 不修改数据库正文。
- 返回 `Result.code = 500`。
